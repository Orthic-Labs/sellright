## 1. Positioning check

**What it is:** a from-scratch, multi-tenant ecommerce backend — TypeScript, Hono 4 typed REST (zod-openapi → OpenAPI contract), Drizzle ORM, Postgres 17, React admin SPA, Qwik storefront. Replaces Vendure for DD first, then RH/TS/SS.

**The architectural bet:** monorepo-modular over microservices; Postgres RLS (FORCE + transaction-local GUC) as the tenancy safety model instead of application-level filtering; typed REST instead of GraphQL; static catalog manifests for browse (zero DB reads); integer-cents money everywhere; owned code instead of Vendure's GPLv3 core.

**Does the code back it? Yes.** `withStore()` (`packages/api/src/db/client.ts:23-38`) is the single gated entry to tenant data; `assert-force-rls.ts` makes the RLS invariant a CI-equivalent gate inside `pnpm verify`; the money path is pure, unit-tested modules; the Vendure import landed cent-perfect ($852,930.51 grand-total parity across 13,481 orders — `docs/STATE-AND-ROADMAP-v1.md` §1.13). vs **Medusa** (tried, rejected pre-Vendure), **Saleor** (GraphQL-first, off-table), **custom**: this IS the custom path, deliberately (`docs/ARCHITECTURE-PLAN-v1.md`, `docs/research/ecom-backend-research-2026-06.md` §2 "composable regret"). The bet is honest in the docs and consistent in the code.

**Honest critique of the bet:** (1) from-scratch means SellRight owns every future commerce edge case Vendure already solved (tax edge cases, partial fulfillments, exchanges); (2) bus factor is 1; (3) the storefront still half-depends on Vendure GraphQL (auth/account/search), so "replacement" is currently a hybrid. See the strategy doc's risk register.

## 2. GOOD (with evidence)

### Tenancy / data layer
- **FORCE RLS on every store-scoped table**, hardened fail-closed predicate `store_id = nullif(current_setting('app.current_store', true), '')::uuid` — unset or reset context → zero rows, never all rows. `drizzle/0002_harden_rls_nullif.sql:6-28`.
- **USING + WITH CHECK on all policies** — cross-store writes rejected at DB level, not just invisible. `0001_rls_policies.sql:17,22`.
- **`SET LOCAL` transaction-scoped GUC** — safe under connection pooling, no context leak between requests. `db/client.ts:28`.
- **Invariant guard in CI-gate:** `db/assert-force-rls.ts:22-43` queries `pg_class` for any store_id-bearing table missing FORCE RLS; runs in `pnpm verify`. A future table can't silently ship unprotected.
- **Dual-pool RLS test suite** — owner role seeds, app role asserts; proves real Postgres RLS, not app filtering. Includes fail-closed (no context → 0 rows) and cross-store WITH CHECK rejection. `db/rls.test.ts:13-18,100-119`.
- **Integer cents everywhere**, tax in basis points, FX rates scaled ×10000 — no float in any money column. `db/schema.ts:169-172,415`.
- **Order-line snapshots** (`variant_sku`, `variant_name`) so history survives variant deletion. `schema.ts:362-363`, `0003_order_line_snapshot.sql`.
- **Migration discipline:** 22 contiguous migrations (0000–0021), idempotent DDL (`IF NOT EXISTS`), RLS hand-applied per migration with comments (drizzle-kit can't model RLS).

### Domain / API layer
- **Checkout idempotency:** `(store_id, idempotency_key)` UNIQUE; concurrent duplicate handled via pg 23505. `routes/checkout.ts:107-113,288-296`, `0007_order_idempotency_and_indexes.sql:6-7`.
- **Pay idempotency:** `processed_event` claimed with `ON CONFLICT DO NOTHING` *before* the gateway call; duplicate = no-op. `routes/pay.ts:57-63`. (But key is optional — see §4.)
- **Coupon double-spend prevented:** `SELECT … FOR UPDATE` on promotion before check+increment. `routes/checkout.ts:196`.
- **Atomic stock reservation:** `UPDATE … WHERE (on_hand - allocated) >= qty` + rowCount check — no oversell. `orders/stock-reservation.ts:38-43`.
- **Central order FSM** — all transitions through `canTransition()`. `money/fsm.ts:5-15`.
- **Refund bounded** by prior-refund sum and order state. `routes/admin-orders.ts:191-192`.
- **Transactional webhook outbox** — delivery rows inserted in the same txn as the business event; HMAC-SHA256 signing; exponential backoff, 6 attempts. `webhooks/emit.ts:13-17,41-57`.
- **Server-authoritative pricing** — unit price from DB, never from client. `routes/checkout.ts:126-148`.
- **Gift card is a tender, not a discount** — can't distort tax/subtotal. `money/gift-card.ts:1-24`, `checkout.ts:256-270`.
- **Admin auth:** httpOnly cookie sessions, double-submit CSRF middleware on all `/v1/admin/*` mutations (`app.ts:31-38`), RFC-6238 TOTP with confirm-before-persist (`auth/totp.ts:42-47`), login rate limit 8 fails/15 min (`auth/rate-limit.ts:1-42`), session tokens stored as SHA-256 only (`auth/session.ts:8,13`), scrypt passwords.
- **RBAC:** owner/manager/staff/read_only + per-action staff permissions (P3, migration 0021). `routes/admin-helpers.ts:42-63`.
- **Audit log** on order/refund/return/stock/product mutations. `admin-orders.ts:125,206,250`.
- **Import path complete and cent-perfect:** catalog/customers/orders scripts from `damned_vendure` (5433 clone), handles Vendure int PKs→UUIDs, DD custom fields, SKU collision suffixing, collection hierarchy. `src/import/catalog.ts`, `customers.ts`, `orders.ts`.
- **Jobs:** dry-run-by-default, overlap-guarded, `JOBS_ENABLED` opt-in. `jobs/scheduler.ts:29-56`.

### Test coverage
- Money suite: 25 cases across totals/tax/gift-card/currency/auto-discount — good pure-function coverage. `money/*.test.ts`.
- RLS suite: 4 tests proving real isolation with dual pools. `db/rls.test.ts`.
- `pnpm verify` = build + typecheck + tests + RLS invariant assert. Root `package.json:12`.

## 3. MISSING — ranked by what blocks production cutover

**Tier 1 — hard blockers for any brand:**
1. **No real payment gateway.** Only `manual`/`cod` exist; NMI/Sezzle/Stripe are TODO stubs. `payments/provider.ts:47-51`. No gateway = no store.
2. **No gateway refund.** `admin-orders.ts:194` inserts a `Settled` refund row without any provider reversal call — refunds are ledger-only; no money returns to the customer.
3. **No transactional email at all.** Zero SMTP anywhere: no order confirmation, shipping notification, password reset, or verification email.
4. **No customer password reset / email verification flows.** `routes/auth.ts` is register/login/google/me/logout only. Compounded by: **imported customers have no passwords** (intentional — `import/customers.ts:1-9`), so ~8.2k migrated customers are locked out at cutover without a reset flow.
5. **Customer CSRF gap.** Admin has global CSRF middleware (`app.ts:31-38`); the shop surface has none — `checkout.ts`, `pay.ts`, `cart.ts` accept cross-site POSTs from a logged-in customer's browser. Only logout checks `customerCsrfValid()` (`auth.ts:175`).
6. **Storefront auth/account/search still on Vendure GraphQL** — those flows fail on pure SellRight (`STATE-AND-ROADMAP-v1.md` §1.11/§3.9).
7. **Ops floor missing:** no systemd units (API + admin run via `nohup`/`setsid`, die on reboot — `scripts-deploy/start-api.sh:11-14`); admin is a Vite **dev server** behind an SSH tunnel, no nginx/TLS; **no automated DB backups** (RPO gate defined in §3A but unwired); no monitoring/alerting (errors → console only, `app.ts:63`).
8. **App still connects as DB owner** — FORCE RLS protects against this, but a single future table missing FORCE would silently leak cross-tenant. Non-owner role fully scripted (`scripts-deploy/create-app-role.sh`), blocked on one sudo on the box.

**Tier 2 — needed soon after:**
9. No asset/object storage — images proxied to DD's Vendure asset server; blocks product-create-with-images (`packages/admin/README.md:38`).
10. No fulfillment webhooks — `order.shipped`/`delivered` never emitted (`routes/admin.ts:254` writes audit only).
11. Rate limiting in-process memory only, and only on login — checkout/pay/register unprotected; resets on restart. `auth/rate-limit.ts:1-8`.
12. No SellRight→Vendure reconciliation exporter (Regime-B rollback after real orders flow).
13. Admin: no product/variant create flow, no image upload.
14. Missing indexes (see §4 perf).

## 5. Recommended order of attack to first cutover

**First brand: Rotten Hand.** Zero existing SellRight orders → greenfield launch, no Regime-B rollback exposure, Stripe (simplest gateway) instead of DD's NMI+Sezzle, no historical-customer password problem at the same scale. DD is the heavier second: NMI tokenized (Collect.js → SAQ-A) + Sezzle, asset migration, parity-replay gate, vault-ref continuity.

Sequence (dependencies, not durations):
1. **Non-owner DB role** — one sudo, script ready. Removes the #1 latent tenancy risk.
2. **Security batch** — shop CSRF middleware, mandatory pay idempotency, IP-header priority fix, seal the unscoped `db` export (fixes 1–4 below).
3. **Stripe provider** + gateway-backed refunds (interface exists; blocked on sandbox key).
4. **SMTP/email service** → password reset, email verification, order/shipping notifications, staff invites.
5. **Storefront rewire** (§3.9): auth → account → search, one flow at a time, Vendure kept warm as Regime-A rollback; customer cookie sessions land with it.
6. **Ops floor:** systemd units, built admin behind nginx + Cloudflare Access, nightly pg_dump + tested restore, uptime check + 5xx alert.
7. **Index batch** (one migration).
8. **RH cutover** behind the §3A gates → then DD prerequisites (NMI/Sezzle, assets, parity replay, reconciliation exporter).

## 6. Implementation guide — top 8 fixes

Snippets use real names from the codebase; verify against current code before applying.

### 6.1 Shop-surface CSRF middleware (`app.ts`)
Mirror the admin guard. Cookie-session requests must double-submit; bearer/no-session (guest) flows pass through:
```ts
// app.ts — after the admin CSRF middleware
import { customerCsrfValid, getCustomerSessionToken } from './auth/cookies.js';

app.use('/v1/shop/*', async (c, next) => {
  const m = c.req.method;
  if (m === 'POST' || m === 'PUT' || m === 'PATCH' || m === 'DELETE') {
    // Only enforce when a customer cookie session is present —
    // guest checkout has no session to ride.
    if (getCustomerSessionToken(c) && !customerCsrfValid(c)) {
      return c.json({ error: 'CSRF token missing or invalid' }, 403);
    }
  }
  await next();
});
```
Exempt `/v1/shop/auth/login` and `/register` (no session yet), same as admin.

### 6.2 Mandatory pay idempotency (`routes/pay.ts`)
Make the key required, or derive one server-side so the guard is unconditional:
```ts
// pay.ts:39 — replace optional header handling
const idemKey = c.req.header('idempotency-key')
  ?? `pay:${code}:${method}`; // deterministic fallback: one in-flight attempt per order+method

// the existing ON CONFLICT DO NOTHING claim at pay.ts:57-63 then always runs
```
Note: the deterministic fallback also blocks legitimate retry-after-decline; on `Declined`, delete the claimed `processed_event` row inside the same txn so the customer can retry.

### 6.3 Seal the unscoped `db` export (`db/client.ts:13`)
```ts
// db/client.ts — rename and brand the escape hatch
/** @internal Owner-context client. Migrations, imports, and jobs ONLY.
 *  Route handlers MUST use withStore(). */
export const unsafeUnscopedDb = drizzle(pool, { casing: 'snake_case' });
// delete the old `db` export; fix the ~handful of legitimate import sites
```
Add a lint rule (`no-restricted-imports`) forbidding `unsafeUnscopedDb` under `src/routes/`.

### 6.4 IP-header priority (`auth/rate-limit.ts:46-49`)
```ts
export function clientIp(c: Context): string {
  // Behind Cloudflare: CF-Connecting-IP is set by the edge and unspoofable.
  // Never trust X-Forwarded-For from the public internet.
  return c.req.header('cf-connecting-ip')
    ?? c.req.header('x-real-ip')          // set by our own nginx only
    ?? c.env?.remoteAddr ?? 'unknown';
}
```

### 6.5 Gateway-backed refunds (`payments/provider.ts` + `admin-orders.ts:194`)
Extend the provider contract, call it before writing the ledger row:
```ts
// payments/provider.ts
export interface PaymentProvider {
  method: string;
  createPayment(input: CreatePaymentInput): Promise<PaymentResult>;
  refundPayment(input: { providerRef: string; amount: number; currency: string })
    : Promise<{ state: 'Settled' | 'Pending' | 'Failed'; providerRef?: string; errorMessage?: string }>;
}
```
```ts
// admin-orders.ts — in the refund handler, before the insert at ~:194
const [payment] = await tx.select().from(s.payment)
  .where(and(eq(s.payment.orderId, order.id), eq(s.payment.state, 'Settled'))).limit(1);
const provider = getProvider(payment.method);
const result = await provider.refundPayment({
  providerRef: payment.providerRef, amount, currency: order.currency,
});
if (result.state === 'Failed') return c.json({ error: result.errorMessage ?? 'refund failed' }, 502);
await tx.insert(s.refund).values({ /* existing fields */ state: result.state, providerRef: result.providerRef ?? null });
```
`manual`/`cod` providers return `{ state: 'Settled' }` no-ops, preserving current behavior.

### 6.6 Webhook scheduler `SKIP LOCKED` (`webhooks/emit.ts:37-60`)
```sql
-- inside deliverWebhooks(), replace the due-rows select:
SELECT id FROM webhook_delivery
WHERE status = 'pending' AND next_attempt_at <= now()
ORDER BY next_attempt_at
LIMIT 50
FOR UPDATE SKIP LOCKED;
```
Process inside the same transaction (or claim via `UPDATE … SET status='processing' … RETURNING`). Pair with the missing `webhook_delivery(store_id, status, next_attempt_at)` index.

### 6.8 Password reset + email verification (`routes/auth.ts` + new `auth/email-tokens.ts`)
Reuse the staff-invite pattern (one-time hashed token + TTL, `admin-settings.ts:458-493`):
```ts
// POST /v1/shop/auth/forgot-password  { email }
// always 200 (no account enumeration); if customer exists:
const raw = crypto.randomBytes(32).toString('base64url');
await tx.insert(s.customerToken).values({
  storeId: st.id, customerId: cust.id, kind: 'password_reset',
  tokenHash: sha256(raw), expiresAt: addHours(new Date(), 2),
});
await sendEmail(st, cust.email, 'password-reset', { url: `${st.config.storefrontUrl}/password-reset?token=${raw}` });

// POST /v1/shop/auth/reset-password  { token, password }
// hash lookup, expiry + used check, scrypt re-hash, invalidate all sessions for the customer
```
Requires a `customer_token` table (new migration, FORCE RLS like the rest) and the SMTP service (Tier-1 #3). This same machinery serves email verification (`kind: 'email_verify'`) and the migrated-Vendure-customer onboarding ("set your password" campaign) — which is the cutover unlock for the 8.2k imported accounts.
