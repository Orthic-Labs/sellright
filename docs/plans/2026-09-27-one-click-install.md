# Proposal: One-Click Install and Guided Setup

**Status:** Proposal for independent review. Nothing here is built yet.
**Date:** 2026-09-27
**Scope:** How a new SellRight owner goes from nothing to a working store, and how they keep it updated and backed up.

---

## 1. Summary

Today, installing SellRight means one command, but only after hand-editing eight values in a hidden file. It needs Docker skills, and it gives you an API and an admin but no storefront.

The proposal is to build **one appliance** with **several one-click front doors**:

- **The appliance** has five parts:
  - prebuilt, signed container images;
  - an installer that generates every machine secret itself;
  - a browser setup wizard, protected by a one-time claim link;
  - store configuration kept in the database, not in files;
  - a host-side helper for updates and backups.
- **The front doors** all run the same installer and land the owner in the same wizard:
  - a cloud marketplace image (DigitalOcean, Hetzner);
  - a PaaS deploy button (Railway, Render, Coolify);
  - a single `curl … | sh` line for any server;
  - a managed hosted option, if Orthic Labs decides to offer one.

**The owner sets exactly one credential, their own email and password, and does it in the browser.** Every other secret is generated by the machine, stored with owner-only permissions, and never shown.

**Answer to "is the admin password the same as the other passwords?":** No. `ADMIN_PASSWORD` is the store owner's login. `POSTGRES_PASSWORD`, `POSTGRES_APP_PASSWORD` and `DOWNLOAD_URL_SECRET` are machine secrets: the database owner, the restricted database login the API runs as, and the key that signs download links. Today the installer has to invent all of them by hand. Under this proposal they stay separate, but the owner never sees or types any of the machine secrets.

**Why not merge them into one password:**
1. **Leak containment.** A phished or reused admin password would otherwise also be the raw database password. That bypasses the row-level store isolation, the audit log and the permission system.
2. **Password changes.** Changing your login password would then mean rotating database credentials under a running system.
3. **Staff.** Stores have many admins, but the database has one owner.
4. **Strength.** Machine secrets should be long random values nobody memorises. A human password is chosen for recall.

## 3. What "one click" should mean

Target experience, measured end to end:

- **No terminal after the entry point.** For a marketplace image or PaaS button, no terminal at all. For a plain VPS, one pasted line.
- **Everything else happens in a browser, over HTTPS**, including before the owner has a domain.
- **A first test order is possible without reading documentation.**
- **Only the owner account and store basics are required.** Every other step can be skipped, and an in-admin checklist brings it back later.
- **Updates and backups are buttons, not runbooks.**

Success measures for the reviewer to hold us to:
1. **Time to a working store:** from "create server" to "test order placed on the storefront", under 10 minutes on a 2 GB VPS with prebuilt images.
2. **Secrets typed by a human:** zero, apart from the owner's own password and any payment or email keys they choose to connect.
3. **Unclaimed-instance exposure:** zero. No state exists in which a stranger can become the owner.

## 4. Options weighed

### 4.1 Entry points

| Option | Owner effort | Reach | Our cost | Control | Verdict |
|---|---|---|---|---|---|
| **A. Managed SellRight Cloud** (we host; SellRight is already multi-tenant with database-enforced isolation) | Sign up, done | Highest for non-technical owners | Highest: we run infrastructure, support, billing, compliance | Low for the owner | **Business decision, later.** The architecture supports it; it's a company choice, not an install feature |
| **B. Cloud marketplace image** (DigitalOcean 1-Click, Hetzner Cloud Apps; both build a snapshot and generate secrets on first boot) | One click to create the server, then the browser | High among self-hosters | Medium: image build pipeline per provider | Full | **Phase 2.** The best true one-click for self-hosting |
| **C. PaaS deploy button** (Railway template, Render blueprint, Coolify/Dokploy templates; variables are generated, the database is provisioned) | One click, then the browser | Developers and agencies | Low: one template file each | Medium | **Phase 3.** Cheap and widens reach |
| **D. One-line installer** (`curl -fsSL https://get.sellright.cc \| sh`) on any Linux server | Paste one line | Every VPS provider | Low once B exists, because B runs the same script | Full | **Phase 1.** The foundation; B and C wrap it |
| **E. Manual Compose** (today) | Edit files, run compose | Experts | Already exists | Full | **Keep** for experts and audits; stop presenting it as the main path |

**Recommendation:** build D and the appliance first, because every other option runs it. Then B for DigitalOcean and Hetzner, then C. A needs its own business case.

### 4.2 Claiming a fresh instance: who becomes the owner?

A freshly installed server is reachable by anyone who finds its address. How the first owner is established is the most important security choice in this design.

| Option | Used by | Problem |
|---|---|---|
| First visitor to the setup page becomes owner | Coolify (documentation warns anyone who reaches registration first gets admin) | Race: scanners find new servers within minutes |
| Setup window that expires (for example, 5 minutes) | Portainer | Still a race inside the window, and owners who are slow get locked out |
| Secret code read from a file on the server | Jenkins (`initialAdminPassword`) | Safe, but needs a terminal: fails the no-terminal goal |
| Credentials passed as installer variables | Coolify (`ROOT_USER_*`), SellRight today | Safe, but the password ends up in shell history or files, and it's not a browser flow |
| **One-time claim link** containing a random token, delivered through a channel only the owner sees | This proposal | None of the above; needs a delivery channel per front door |

**Recommendation: a one-time claim link.** How the owner receives it depends on the front door:

- **One-line installer:** it's printed at the end of the install, with a QR code.
- **Marketplace image:** it's shown in the server's login banner and the provider's console output, and optionally emailed when the provider passes an email in user data.
- **PaaS:** it's generated into a `SETUP_CLAIM_TOKEN` variable, visible only in the owner's dashboard.
- **If the link is lost:** `sellright setup-link` prints a new one (host access required).

**Rules:**
- The token is 128-bit and random, and only its hash is stored.
- It's single-use and rate-limited, and is invalidated the moment an owner exists.
- Until it's claimed, the whole admin and API refuse everything except `/setup` and health checks.
- After claiming, every `/setup` route returns 404 permanently.

### 4.3 HTTPS before the owner has a domain

The owner will type a password in the first minute, so it must travel over HTTPS, even though most owners won't have pointed a domain yet.

| Option | Problem |
|---|---|
| Plain HTTP on the IP address | Password sent in clear text. Rejected |
| Self-signed certificate | A frightening browser warning on the very first screen. Rejected |
| Wildcard-DNS hostname such as `1-2-3-4.sslip.io` (Coolify's default) | Shared Let's Encrypt rate limit has been exhausted in practice; sslip.io is deliberately not on the Public Suffix List, so sibling sites can set cookies on the parent domain |
| **Let's Encrypt IP-address certificate** (6-day certificates, generally available since 2026-01-15; supported by current Caddy) | Needs automatic renewal, which Caddy does. Must be confirmed with a spike on the pinned Caddy version |
| Our own free subdomain service (`<store>.sellright.app`) | Best experience, but Orthic Labs has to run DNS and certificates for everyone. It fits option A |

**Recommendation:** use a Let's Encrypt IP certificate for setup; the wizard's Domain step then attaches the real domain. A free hosted subdomain can come later, as a convenience tied to the managed or registered offering.

The **Domain step** does four things:
- shows the exact DNS record to add;
- checks it live, including whether Cloudflare's proxy is on;
- issues the certificate;
- redirects the IP address to the new domain.

### 4.4 Where configuration lives

**Today** everything is in environment files, which only a technical operator can edit and which need restarts.

**Proposed split:**

- **Environment (infrastructure only):**
  - database URLs;
  - one **master encryption key**;
  - listening ports.

  The installer writes these to a root-owned `600` file; nobody edits them.
- **Database (everything an owner might change):**
  - store name, currency, domains;
  - payment accounts, email (SMTP), captcha, CDN purge credentials;
  - feature settings.

  Secret fields are **encrypted with the master key** (authenticated encryption, key rotation supported) and are edited in the admin with test buttons. The admin never shows a secret again after saving, only the last 4 characters.

**Precedence during migration:** an environment value, if present, overrides the database and shows as "managed by server configuration" in the admin. Existing deployments keep working unchanged.

### 4.5 Payments

| Option | Pros | Cons |
|---|---|---|
| **Paste keys, then SellRight finishes the setup** | Works for every self-hosted install; no dependency on Orthic Labs | The owner must find the keys in their Stripe dashboard |
| Stripe Connect ("Connect with Stripe" button) | The smoothest experience | Orthic Labs becomes a Stripe platform and a runtime dependency for every self-hoster. Stripe no longer recommends OAuth for new platforms, and hosted onboarding means platform-managed accounts |

**Recommendation for self-hosting: paste keys, with guided finishing.**

**Stripe:**
1. The owner pastes a restricted key, and we link directly to the Stripe page where it's created.
2. SellRight checks the key.
3. SellRight **creates the webhook endpoint through Stripe's API**; the signing secret comes back only once, at creation, and is stored encrypted.
4. SellRight defaults the store to test mode and offers "Place a test order".

The owner never handles a webhook secret.

**Other providers:** NMI and Sezzle use the same pattern (paste, check with a harmless API call, test mode first), and "manual / cash on delivery" needs no keys.

**Connect** fits the managed option (A), where Orthic Labs is the platform anyway.

### 4.6 Email

- **Presets:** Google Workspace/Gmail (app password), Amazon SES, Postmark, Resend, and custom SMTP.
- **Checks:** the wizard sends a real test message and shows the provider's error in plain language if it fails.
- **Skippable, with a clear warning** that order emails and password-reset emails won't send. The `sellright reset-admin` command covers owner lock-out.

### 4.7 Storefront

This is the biggest functional gap today: an install contains no shop.

- **Add the generic storefront to the appliance** as its own service behind Caddy, on the same domain or a subdomain.
- **Offer three storefront choices in the wizard:**
  - the built-in storefront;
  - built-in storefront plus sample products, so the owner can see a working shop immediately and delete the samples in one click;
  - headless ("I'll bring my own front end"), which shows the API URL and a publishable key.

### 4.8 Updates

| Option | Problem |
|---|---|
| Docker socket mounted into a container (Watchtower-style) | Equivalent to giving that container root on the host |
| "Run these commands" | Not one click |
| **A small host service installed by the installer**, which the admin can only *request* an update from | Recommended |

**How an update works:**
1. The admin shows "Version X available" with release notes. Releases come from a **signed release manifest**, and images are verified against their signatures before use.
2. On "Update", the host service:
   - takes a backup;
   - pulls the images;
   - runs migrations (as today, owner role first);
   - health-checks the new version;
   - **rolls back automatically** if the health check fails.
3. **Automatic minor and security updates are optional and off by default.**

### 4.9 Backups

- **On by default:** nightly database and asset backups to a local volume with retention.
- **Optional off-site copy** to any S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2), encrypted before upload. It's configured in the wizard or later.
- **Restore** from the admin (pick a snapshot) or with `sellright restore`.
- **A monthly automatic restore check** into a throwaway database, shown on the admin dashboard, so owners know their backups actually restore.

## 5. Proposed owner journey

### Entry
- **Marketplace:** choose "SellRight" and pick a size (2 GB minimum). The server boots and the installer runs automatically. The claim link appears in the provider console.
- **VPS:** paste `curl -fsSL https://get.sellright.cc | sh`. The installer:
  - checks the operating system, memory, disk and free ports 80/443;
  - installs Docker if it's missing;
  - generates all secrets;
  - pulls signed images;
  - starts services;
  - prints the claim link and a QR code.
- **PaaS:** click the deploy button. The platform generates the variables and the database. The owner opens the app URL; the claim token sits in their dashboard.

### Setup wizard (browser, HTTPS)

| # | Step | Required? | What it asks | Smart defaults |
|---|---|---|---|---|
| 1 | Welcome | Yes | Nothing; the claim token comes from the link | Checks the system and shows a green list |
| 2 | Owner account | Yes | Name, email, password with a strength meter (12+ characters, matching today's rule), then offers two-factor | Two-factor strongly suggested, not forced |
| 3 | Store basics | Yes | Store name, country | Country sets currency, units, timezone and a tax starting point |
| 4 | Domain | Skippable | Custom domain | Shows the DNS record and checks it live |
| 5 | Payments | Skippable | Provider and keys | Test mode on; webhook created automatically |
| 6 | Email | Skippable | Provider preset | Test email sent |
| 7 | Shipping & tax | Skippable | Flat rate, free-shipping threshold | Based on country |
| 8 | Storefront | Skippable | Built-in, built-in with sample products, or headless | Built-in with samples |
| 9 | Backups | Skippable | Optional off-site bucket | Local nightly backups already on |
| 10 | Launch | — | "Place a test order", then "Go live" | Switches payments to live after a successful test |

The wizard saves after every step and can be resumed. Skipped steps become a **setup checklist on the admin dashboard** (the Shopify pattern) until they're done or dismissed.

### After setup
- **Admin → Settings:** every value from the wizard can be edited there, with the same test buttons.
- **Admin → System:** version, update button, backups, restore check, health.
- **`sellright` command on the host, for experts and recovery:** `status`, `logs`, `update`, `backup`, `restore`, `reset-admin`, `setup-link`, `uninstall`.

## 6. Security requirements for review

1. **Claiming:** no state in which an unclaimed instance accepts anything but `/setup` and `/health`. The claim token is hashed, single-use and rate-limited. `/setup` is gone forever after claiming.
2. **Transport:** no password or secret is ever submitted over plain HTTP. The wizard refuses to load except over HTTPS.
3. **Separate secrets:** each machine secret is independently random, at least 256 bits where it's a key, and never shown to a human. The database's owner and app roles stay split, as today.
4. **Encryption at rest:** integration secrets in the database are encrypted under the master key with authenticated encryption and a key version for rotation. The admin only ever shows a masked value.
5. **Supply chain:** images and the release manifest are signed; the installer and updater verify signatures and pin image digests. The installer script is served over HTTPS from a pinned domain, with a published checksum for people who want to inspect it first.
6. **Least privilege:** the updater is a host service with a narrow command set. No container gets the Docker socket.
7. **Audit:** claiming, changes to the owner account, secret changes, updates and restores all write to the existing audit log.
8. **Privacy:** no telemetry by default; anonymous install counting only with opt-in.

## 8. Open questions for the owner and reviewers

1. **Licensing:** SellRight is a public repository sold as a commercial product. Does setup need a licence-key step (for paid tiers), or is the self-hosted edition free with paid support or a managed option? This changes step 1 and the release manifest.
2. **Hosted subdomain:** should Orthic Labs run a free `<store>.sellright.app` service for new installs, as an alternative to IP certificates?
3. **Minimum server size:** is 2 GB right once the storefront is included? It needs measuring during phase 1.
4. **Multi-store:** SellRight supports many stores per install. Should the wizard offer "add another store" at the end, or leave that to the admin?

## 9. How to verify this proposal

Reviewers should check three kinds of claim:

1. **"What exists today" (section 2)** against the cited files.
2. **The security requirements (section 6)** against the claim-race and supply-chain risks described in 4.2 and 4.8.
3. **The external facts** against the sources below:
   - Let's Encrypt IP certificates;
   - Stripe webhook creation returning the secret only at creation;
   - Stripe's current guidance on Connect OAuth;
   - how Coolify, Portainer and Jenkins handle first-run claiming;
   - DigitalOcean and Hetzner first-boot image behaviour.
