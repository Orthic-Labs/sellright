# Migrations runbook

## Hand-written migrations (ra-006)

Five migrations in `packages/api/drizzle/` are hand-written and MUST NOT be
regenerated by `drizzle-kit generate`:

| File                                | Why hand-written                                                                                                              |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `0032_cart_ttl.sql`                 | `drizzle-kit generate` misfires on the cart table — emits ALTERs that don't match the post-0031 schema and break fresh-DB migrate. |
| `0034_subscriptions.sql`            | Auto-generator places the FORCE RLS / tenant policy at a different ordinal; ENUM placement also drifts.                       |
| `0036_harden_subscription_rls.sql`  | `ALTER POLICY` in place; auto-generator prefers DROP + CREATE which races with concurrent connections.                         |
| `0037_payment_provider_ref_unique.sql` | Partial unique index (`WHERE provider_ref IS NOT NULL`) — drizzle-kit does not model partial indexes (same class of gap as the `license_activation_token_hash` index from migration 0027) and can never generate or safely diff this file. |
| `0038_email_outbox.sql`             | REL-4 email outbox for the order-confirmation retry/dead-letter pattern (DISPATCH.md lane REL-4). Schema mirrors `webhook_delivery` but with no endpoint FK — auto-generator would either reuse the webhook table or emit the FORCE RLS policy at the wrong ordinal. Hand-authored to land the table + index + tenant policy atomically. |

Each file starts with a marker comment:

```sql
-- HAND-WRITTEN: see docs/runbooks/migrations.md — do NOT regenerate via drizzle-kit.
```

The `pnpm db:assert-hand-written` script greps for this marker in every
hand-written migration and fails CI if it's missing or has been silently
replaced. Run it locally before opening a migration-touching PR:

```bash
pnpm --filter @sellright/api db:assert-hand-written
```

## When to use the custom workflow

Default workflow (use 99% of the time):

```bash
# 1. Edit schema in packages/api/src/db/schema*.ts
# 2. Generate the migration
pnpm --filter @sellright/api db:generate
# 3. Review the diff in packages/api/drizzle/<auto>.sql — sanity-check that
#    it doesn't touch any of the hand-written file's tables / policies.
# 4. Apply to dev DB
pnpm --filter @sellright/api db:migrate
```

Custom workflow (only for the three hand-written files):

1. Open the existing `<NNNN_*.sql>` file directly.
2. Edit the SQL in place. Do NOT run `db:generate`.
3. If the schema in `schema*.ts` actually changed in a way that warrants a
   separate migration, bump the migration number on a NEW file — leave the
   hand-written file untouched.
4. Re-run `pnpm db:assert-hand-written` to confirm the marker is intact.

## What "do not regenerate" actually means

- ❌ `drizzle-kit generate` rewrites a hand-written file.
- ✅ Editing a hand-written file directly (with the marker preserved).
- ✅ `drizzle-kit generate` producing a NEW file (next number) that touches
  unrelated tables.

## If a future schema change is incompatible with a hand-written file

The hand-written file is a frozen contract. If the schema underneath drifts
enough that the hand-written file's SQL would no longer apply cleanly, the
right move is to:

1. Land a NEW migration that does the diff bridge (e.g. add the new column).
2. Leave the hand-written file alone. Future agents can reason about "what
   did this migration do at the time it landed" from the file itself.
3. Open an issue to eventually de-hand-write the migration once enough
   changes have accumulated to make a regeneration safe.
